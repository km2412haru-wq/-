## 機能1: 前駆症状の順列トラッキング

### 設計案
**方針: 新しい入力負担をほぼ増やさず、「発症日」を持たせる。順序は日付から導く。**

- 発熱・倦怠感・関節痛・皮疹は、既存フィールド(`temperature`≥38 / `fatigueUnusual` / `jointPain` / `rash`)から「初出日」を**派生**できる。新規入力は不要。
- 症状(`symptoms`)だけに、任意の`onsetDate`(その症状が始まった日、YYYY-MM-DD)を追加する。日次記録より前から続いている症状(「3日前から喉が痛い」)を遡って表現するため。

```ts
interface SymptomEntry {
  name: string; severity: 1|2|3|4|5; unusualNote?: string;
  onsetDate?: string;            // 追加(任意)。未設定なら「この記録日から」とみなす
}

// 新規 lib/symptomSequence.ts(派生関数のみ、保存はしない)
interface OnsetEvent { kind: "symptom"|"fever"|"fatigue"|"jointPain"|"rash";
                       name: string; onsetDate: string; source: "declared"|"derived"; }
deriveOnsetEvents(logs): OnsetEvent[]      // 各症状の「連続して現れ始めた最初の日」
groupIntoEpisodes(events, gapDays): OnsetEvent[][]   // 症状の無い期間で区切った再燃エピソード
toSequence(episode): string[][]            // 日付順。同日は同じ段に並べる(例: [["喉の痛み"],["倦怠感","発熱"],["関節痛"]])
```

- **入力UI**: 症状を選ぶと小さく「いつから? [今日][昨日][2日前][3日以上前→日付]」。**既定は「今日」なので追加タップはゼロ**。遡りたい時だけ1タップ。
- **将来の分析**: 保存されているのは`onsetDate`と既存の日次記録だけ。エピソード分割・順列化は派生関数で後から何度でも再計算できる(分析ロジックを変えても保存データの移行が要らない)。

### 検討して採用しない案
| 案 | 不採用の理由 |
|---|---|
| 配列順(チップをタップした順) | 同じ画面で選んだ順に意味は無い。発症順とは無関係 |
| `onsetOrder`(連番) | 日をまたぐと矛盾し、後から修正・並べ替えが困難 |
| 入力時刻(`recordedAt`)で自動順序付け | 入力した時刻であって発症時刻ではない。後入力で崩れる |

### 制約
- 粒度は日単位。同日に始まった症状の前後は区別しない(区別するには時刻入力が要り、入力負荷が大きい)。
- 毎日記録しない人では、「初出日」が実際より遅く出る。`source: "derived"`で区別し、分析時に確度を下げて扱えるようにする。

### 既存の再燃検知(`lib/emergencyCheck.ts`)への組み込み
現状のF10は、ルートA/Dが「直近7暦日の窓での発熱・倦怠感の日数カウント」、ルートCが「最新記録と直前3件の比較」。順列を使うなら**新ルートE**を足す形になる。変更箇所は次のとおり。
- `EmergencyReasonGroup.category`のunionに1つ追加、ルートE本体を追加、`triggered`の論理和に追加
- `EmergencyBanner`はカテゴリを汎用的に描画しているため、変更はほぼ不要
- テストにルートE分を追加

**ただし、今回はF10への組み込みを推奨しない**。
- 要件定義書のとおり本人は風邪をひきやすい体質で、「喉の痛み→倦怠感→関節痛」は風邪でも起きうる。パターンが未知のまま順列で発火させると、偽陽性で警告疲れを起こし、本当の警告が埋もれる。
- 「よくある順列パターン」は、データが貯まって分析して初めて分かる。
- 提案: 今回は**データ構造と派生関数まで**。F10への組み込みは、過去の実際の再燃エピソードを見て、パターンが確認できてから(暫定案は「直近5日以内に新規に現れた異なる系統が3つ以上」)。

**コスト: 中 / 入力負荷: 既定なら増えない**

## 機能2: フェリチン/ESR比の自動計算

### 出典の確認結果(重要)
- **一次資料は未確認**。この環境からは論文本文のサイト(Frontiers、PMC)に到達できず、検索結果の要約のみ確認した。
- 検索結果からは、次のことが読み取れる。
  - 「フェリチン/ESR比>21.5」は、**小児の全身型若年性特発性関節炎(sJIA)のMAS**を見分ける指標として報告されたとする記述がある(感度82%・特異度78%とされる)。出典は総説 [Frontiers in Immunology 2024](https://www.frontiersin.org/journals/immunology/articles/10.3389/fimmu.2024.1389710/full) の記述。
  - 同じ「フェリチン/ESR比」でも、研究によって**カットオフが異なる**(sJIA新規発症でMASを見分ける「>80」とする報告あり。[Eloseily et al., ACR Open Rheumatology 2019](https://acrjournals.onlinelibrary.wiley.com/doi/abs/10.1002/acr2.11048))。
  - 成人AOSDでは、フェリチン/ESR比(FER)を臓器障害の予測指標の一つとして評価した研究がある([PMC11508950](https://pmc.ncbi.nlm.nih.gov/articles/PMC11508950/))が、**21.5がAOSDに妥当かは未確認**。
- 結論: **21.5は「小児sJIAの報告値」で、成人AOSDへの適用は未検証**。コード内コメントとアラート文言にこの旨を明記する。

### 設計案
- データ: `labs.esrMmH?: number`(mm/h)を追加(追加のみ)。
- 計算: 同じ日の記録でフェリチン>0かつESR>0の両方がある場合のみ、`ratio = フェリチン(ng/mL) / ESR(mm/h)`。**別の日の値を組み合わせない**(別の採血同士の比は意味を持たない)。ESRが0や未入力なら計算しない(0除算を避ける)。
- 閾値は定数`FERRITIN_ESR_RATIO_REFERENCE = 21.5`とし、上記の出典状況をコメントに明記する。
- **CRPは式に使わない**(依頼文の「CRP・フェリチン・ESRから」は式にCRPが登場しないため、CRPは従来どおり入力・表示のみ、という解釈。要確認: Q3)。

### 表示方法の選択肢(Q2)
| 案 | 内容 | 評価 |
|---|---|---|
| **(b) 参考表示のみ(推奨)** | 入力フォームの検査値欄・記録一覧・レポートに「比: 24.1(参考値)」を表示し、超過時は中立色の注意書きを添える。赤いF10バナーは出さない | 出典が小児・未検証のため、赤バナーで「受診を検討」と言い切るのは過大 |
| (a) F10のルートBに追加 | 検査値カテゴリの理由として赤バナーに出す | 誤報が警告疲れを招くリスク。出典確認後に格上げする余地は残せる |

- 文言案(超過時): 「フェリチン/ESR比が21.5を超えています(参考値: 小児の全身型若年性特発性関節炎のMASで報告された基準で、成人AOSDでの有効性は確認できていません)。他の検査値と併せて、主治医へ共有することを検討してください」
- 受け入れ側の整合: 「(a)」を選ぶ場合は、複数系統の異常数(`multipleLabAbnormal`)に**数えない**(未検証の指標で「強い注意喚起」を出さないため)。

## 機能3: 低エネルギーモード(簡易入力)

### 設計案
- データ: `DailyLog.entryMode?: "quick" | "full"`(未設定は"full"扱い、追加のみ)。簡易記録も通常と**同じスキーマ**に保存する。
- **簡易フォームの項目(推奨の最小セット)**
  1. 体調スコア(1〜10の大きなボタン)
  2. 「普段と違う強い倦怠感」(トグル1つ) ← F10ルートA/Dの主入力
  3. 症状: なし/あり(ありなら頻度順のチップ)
  4. **危険な症状(常に表示、折りたたまない)** ← Danger層。最悪日こそ必要
  5. 体温(任意、数値1つ) ← F10ルートAの入力
  6. 保存ボタン1つ
- 保存時に自動で行うこと: 対象日=今日、定期薬は該当薬を**「未確認」で自動追加**(記録していない=服用ではない。3状態の考え方と整合。こうしないとレポートの服用状況から簡易記録の日が見えなくなる)。
- **F10との整合(重要)**: 簡易記録は「記録があるがこれらの項目は未入力」の日になる。
  - ルートA/D(陽性日のカウント方式): 未入力を「なし」と読んでも偽陰性は出ない(数えないだけ)。問題なし。
  - ルートC: 簡易記録は`jointPain`が空なので、ベースラインに入ると「新規部位」の誤判定の原因になる。**簡易記録はルートCのベースラインから除外**する。
  - データ不足の判定(`dataQuality`): 簡易記録は体調スコアがあるので「記録日」に数える(要確認: Q4)。

## 実装で判明したこと(承認後の追記)

- **ブラウザ確認で見つけた不具合(機能3の実装中)**: `useDailyLogs`等のフックは、読み込んだだけのインスタンスも読み込み直後に保存し直していた。簡易保存の直後に通常フォームが作り直されると、その中のインスタンスが古い一覧を読み込んで書き戻し、追加した記録が消えた。5つのフックを「変更操作をしたインスタンスだけが保存する」方式に修正し、修正前の挙動で失敗する回帰テストを追加した。
- **P0の不具合(先に直した)**: 復旧通知のバナーが各ページのデータ読み込みより先に初期化されるため、通知が次回起動まで遅れていた。起動時に自分で整合性チェックを行う`verifyStoreOnStartup`に変更した。
- **機能2に伴う既存の不具合**: 検査値の一括インポートで、読み取れなかった項目が、その日の既存の検査値を消していた。修正した。
- **機能2の出典**: 一次資料は最後まで未確認(論文サイトに到達できず)。確認できた範囲では21.5は小児sJIAのMASの基準で、成人AOSDでの妥当性は未検証。参考表示にとどめ、F10には使っていない。
