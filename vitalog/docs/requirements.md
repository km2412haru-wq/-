# Vitalog 要件定義書

2026年9月28日 作成者: @もり

## 背景・目的

開発者本人は成人発症スティル病（指定難病54、通称AOSD）の患者。発病から5年が経過し現在は比較的安定しているが、風邪をひきやすく治りにくい体質と、関節痛が頻発する特性を持つ。

大学入学後、通学時間6時間に加え部活・ゼミ・アルバイト・資格勉強・授業を詰め込んだ生活リズムの乱れが引き金となり症状が再燃した経験があり、日々の生活パターンと症状の関係を定量的に把握し予防に繋げたいという動機からVitalog開発に至った。

設計思想の参考として、筑波大学・落合陽一氏が実践する「定期健診数値の記録・可視化」「睡眠時間などの自己実験によるフィードバックループ」という、データドリブンな自己観察（セルフハッキング）の手法を取り入れる。

## 対象ユーザー・利用シーン・スコープ

| 項目 | 内容 |
|---|---|
| 対象ユーザー | 開発者本人のみ（単一ユーザー、認証機能はMVPでは不要） |
| デバイス | Android（PWAとして開発、将来的なネイティブ化も検討） |
| 利用シーン | いつでも記録可能（1日1回に縛らない）、後入力・スキップ可 |
| スコープ | MVPとしてF1〜F12の全機能を一括実装（段階リリースはしない） |
| 将来の変化点 | 2027年よりAmazon Japanオペレーション職に従事予定。シフト制等の就業形態変化や、学生→社会人という生活リズムの大きな変化を見据えた設計とする |

## 設計方針

- **疾患特化型設計**：汎用疾患管理エンジン化はしない。成人スティル病は完治しない慢性疾患であるため、将来の他疾患への拡張性よりも、山口基準等に基づく成人スティル病への深い最適化を優先する。
- **パーソナライズOS思想**：初期知識（山口基準等一般疾患知識）を土台とし、記録の蓄積に伴い個人の基準値・悪化トリガー・回復パターンを学習していく。使うほど自分専用に進化する体の取扱説明書。
- **データ引き継ぎを重視**：セキュリティ強化よりも、仕様変更時のマイグレーション容易性を優先した設計（データ構造にバージョン番号を持たせる）。
- **継続性最優先**：慢性疾患であることを踏まえ、精密な記録よりも長期的な記録継続を可能にするUX（ざっくり入力、60秒以内入力、スキップ可能）を重視する。

## 各機能要件の詳細仕様

### F1：毎日の体調記録

- 必須：体温、体調スコア（1〜10）、関節痛（部位：膝・手・足・肘・肩・その他＋強さ）、咽頭痛（普段と違う感覚を検知したい重要項目）
- 任意（低優先度）：皮疹（写真添付は実験的機能として実装し精度を検証）、筋肉痛、リンパ節の腫れ
- 気分スコア（1〜10、常時表示）、落ち込み理由タグ（スコアが一定値以下の時のみ条件表示、体調不良/人間関係/将来不安/疲労/特になし等）
- 服薬記録、自由メモ（Web Speech APIによる音声入力を任意で採用し、標準のLLMタグ付け処理で構造化）
- 入力タイミングはいつでも可。後日入力・「今日はスキップ」の両方を許容

### F2：服薬記録

- 定期薬と頓服を区別、用量・時刻を記録
- 減薬・増薬（テーパリング）履歴を保存
- 服薬リマインダー通知

### F3：環境データ取得

- 気温・気圧・湿度を天気API（例：Open-Meteo）から自動取得

### F4：データ可視化

- 体調スコア・症状の時系列トレンドグラフ

### F5/F11：相関分析・データサイエンス基盤

- pandasでの前処理・特徴量エンジニアリング（ラグ特徴量・移動平均等）
- ラグ相関分析（時差相関）で「何が何日後の症状に影響するか」を検出
- データ量に応じて分析を段階的に解禁：〜30日は単純集計のみ、30〜90日で基本相関、90日〜で重回帰・特徴量重要度、1年〜で季節性分析

### F6：アラート／予測

- 蓄積データから学習した個人のベースライン・閾値に基づく予防的通知

### F7：医師向けレポート出力

- PDF/CSV出力（利用頻度低い想定のため、内容仕様は非規定）

### F8：データ管理

- Google Driveへの定期自動バックアップ
- CSV/JSON形式でのエクスポート
- データ構造にバージョン番号を持たせ、仕様変更後も旧データを読み込めるマイグレーション機構を実装

### F9：スケジュール・負荷管理

- 今日の負荷感（3段階：暇・普通・過密）、活動タグ（授業・バイト・部活・ゼミ・資格勉強・仕事・通勤・シフト等、将来の職業変化に対応してカスタマイズ可能）、睡眠時間（独立の毎日スライダー）
- 時間単位の精密な記録はしない（慢性疾患の長期継続を優先）

### F10：緊急時検出・受診推奨

- MAS（マクロファージ活性化症候群）等の重篤合併症パターンを、通常のトレンド分析とは別系統でリアルタイム判定
- 高熱の持続＋いつもと違う強い倦怠感＋（検査値入力時）フェリチン・血小板等の急変を組み合わせて判定
- 出力は「診断ではなく受診推奨」として明確に、判定根拠とともに透明性を持たせて表示
- 緊急連絡先への自動通知、音声入力の必須化は不採用

### F12-1：仮説検証フレームワーク

- 「気圧低下を3日後に関節痛」のような仮説を自分で登録し、データ蓄積に応じて支持率をフィードバック

### F12-2：セルフA/Bテストログ

- 「今週は睡眠を20分増やす」等、意図的な介入期間を宣言し前後で体調スコアを比較

### F12-3：年次振り返りレビュー

- 1年間の記録をもとにLLM（低頻度のためSonnet想定）が物語的な振り返りを生成

### F12-4：ライフステージ移行監視モード

- 2027年のAmazon Japan入社前後の数ヶ月を「要注意期間」として自動フラグ、普段よりも敏感な閾値で検知（高校→大学の生活変化で再燃した実体験に基づく）

### F12-5：健康×生産性相関記録（任意）

- その日の成果実感を軸で記録し、体調スコアとの相関を検証。F12-1の仮説検証精度向上にも寄与

## 非機能要件・対象外機能

### 非機能要件

| 項目 | 内容 |
|---|---|
| 認証 | MVP段階では不要。将来のマルチユーザー化を見据えたデータ構造とする |
| セキュリティ | 最小限。暗号化よりもデータの引き継ぎやすさ（マイグレーション容易性）を優先 |
| バックアップ | Google Driveへの自動バックアップ。端末紛失・アンインストール時も復元可能に |
| データバージョン管理 | 記録項目・データ構造にバージョン番号を持たせ、仕様変更後も旧データを破棄せず読み込めるようにする |
| リマインダー通知 | 記録忘れ防止のための優しい通知（強制ではない） |
| LLM連携のコスト最適化 | 頻度に応じてモデルを使い分け（日次処理＝Haiku、週次・月次分析＝Sonnet）。生データではなく統計サマリーをLLMに渡しトークン消費を抑制 |

### 明示的に対象外（やらないこと）

- 月経周期の記録（該当なし）
- 緊急連絡先への自動通知
- 音声入力の必須化（任意機能としてのみ採用）
- 詳細な画面遷移図・画面一覧（実装フェーズで決定）
- 医師向けレポートの詳細仕様（利用頻度低い想定のため非規定）
- 厳密な完成判定基準（受け入れ基準）（簡易ローンチのため規定しない）
- 英語学習機能との統合（コアの軸をぶらすリスクを優先し不採用）

## 技術方針・将来のAWSアーキテクチャ構想

### MVP（今回）

- Android向けPWAとしてClaude Codeで開発、デプロイはVercel（普段のローンチ環境）を利用。安定稼働後にAWSへの移行を学習・ポートフォリオプロジェクトとして計画する
- データサイエンス：pandas、scipy.stats/statsmodels、matplotlib/plotly
- 音声入力：Web Speech API（ブラウザ標準、無料）→既存のLLMタグ付け処理に流用

### 将来のAWS移行構想（参考・ポートフォリオ学習プロジェクト）

| サービス | 役割 |
|---|---|
| S3 + CloudFront | PWAの静的ファイル配信 |
| API Gateway + Lambda | サーバーレスAPI、分析処理 |
| DynamoDB | 体調・服薬・スケジュール等のデータ保存 |
| Cognito | 将来のマルチユーザー化時の認証管理 |
| SNS | アラート・緊急通知の送信 |

個人利用・低トラフィックならAWSのAlways Free枠（Lambda月100万リクエスト、DynamoDB 25GB等）内で運用できる見込み。運用開始後もAWS公式の最新料金ページで定期確認する。

このAWS移行プロジェクト自体が、AWS SA・アプライドサイエンティストを目指す上での実践経験になる。

## アプリ名・公開方針（ポートフォリオ戦略）

アプリ名：Vitalog（Vital + Log）

### 公開方針

- コードはGitHubで公開し、AWS SA・アプライドサイエンティスト志望のポートフォリオとして活用する
- 個人の医療データ本体は一切非公開とし、.gitignoreでリポジトリから除外する
- デモ・採用面接向けにはダミーデータを使用する
- READMEやnote.com等で、要件定義からの設計思想・意思決定プロセスを記録し、SEとしての設計力をアピールする

## 実装方針（Claude Code活用）

- 定型的な部分（画面CRUD、PWA雛形、UIコンポーネント）はClaude Codeに任せる
- コアロジック（F5/F11の相関分析、F12-1の仮説検証、F10の緊急検出ロジック）は自分で設計・理解しながら進める（ポートフォリオとして説明責任を果たせるようにするため）
