## 事前調査A: 日付の扱い(UTC依存)

### 結果(実行して確認したもの)
| 確認 | 方法 | 結果 |
|---|---|---|
| フォームの「対象日」 | 実ブラウザ(本番ビルド、`timezoneId: Asia/Tokyo`、時刻固定) | JST 00:30 と 08:59 は既定値・`max`とも**前日**。09:01 と 23:30 は正しい。簡易入力(`QuickLogForm`)も同じ関数 |
| `addDays`(`lib/report.ts`, `lib/correlationAnalysis.ts`) | `TZ=UTC / Asia/Tokyo / America/New_York`で同じ入力を実行 | UTCとNYは正しい。**JSTだけ、睡眠不足の翌日に症状あり: 0%(正: 100%)、それ以外: 100%(正: 0%)**。相関のラグも1日ずれる(`addDays(x,0)`が前日、`addDays(x,1)`が当日を返す) |
| 自己実験の比較・トレンドの期間フィルタ・ライフステージ判定 | 同上 | UTCとJSTで結果が一致(問題なし) |

**原因**: `new Date(\`${date}T00:00:00\`)`(端末の時刻として解釈)を`setDate`してから`toISOString()`(UTC)で日付に戻している。東の時刻帯(日本)では、ローカルの0時がUTCの前日になるため、必ず1日戻る。**テストはコンテナのUTCで動くため、これまで検出できなかった**。実利用者の端末(JST)ではレポートが間違った内容を医師に見せる。

### 洗い出し(`toISOString().slice(0, 10)`等、UTCの日付を「今日」として使う箇所)
| 影響 | 箇所 |
|---|---|
| **要修正(JSTで結果が誤る)** | `lib/report.ts` `addDays` / `lib/correlationAnalysis.ts` `addDays` |
| **要修正(0〜9時に前日になる)** | `DailyLogForm.tsx` `todayIso`(対象日の既定値・`max`) / `QuickLogForm.tsx` `todayIso` / `MedicationsManager.tsx`(処方開始日の既定・中止日・テーパリング日) / `MedicationNotebookUpdater.tsx` / `VisitsManager.tsx`(受診日の`max`) / `ExperimentsManager.tsx`(実験の開始・終了日) |
| **判定の「今日」がUTC(9時間ずれるが、フォームと同じUTC基準のため内部では整合)** | `lib/emergencyCheck.ts` / `lib/dangerCheck.ts` / `lib/lifeStage.ts` / `lib/selfExperimentAnalysis.ts` / `lib/trendData.ts` / `lib/environment.ts`(現在値APIと過去日APIの切り替え) |
| 実害なし(偶然安全、または表示のみ) | `useVisitReminders`(9時台のみ動くため、UTCの日付がJSTと一致する) / `useForegroundReminders`(重複防止のキーのみ) / ファイル名の日付 / `onsetChoice`・`symptomSequence`(`T00:00:00Z`で統一済み) |

**実害**: 朝7時に測った体温を記録すると、対象日が**前日**になり、前夜の記録と同じ日付の2件目になる(F10は日数を「記録件数」で数えるため、同じ日の発熱・倦怠感が二重に数えられる)。睡眠の「翌日」の対応もずれる。

### 設計案
- 新規`lib/dateUtil.ts`: `localTodayIso()`(端末のローカル日付。`getFullYear/Month/Date`)、`addDaysIso(date, n)`(日付文字列の純粋な計算。UTC演算)、`daysBetweenIso`。**日付文字列をDateに変換する時は必ず`T00:00:00Z`、今日の取得は必ずローカル**という規則を一箇所に集約する。
- 上記の全箇所を置き換える。`checkEmergency`・`checkDanger`は「今日」を引数で受け取れるようにする(指摘3の再利用にも必要)。
- 「今日」は**端末のローカル日付**とする(海外滞在時は現地の日付になる。固定タイムゾーンの設定は今回は見送り。Q-A2)。
- 二重カウントの是正: F10の発熱・倦怠感の日数は、記録**件数**ではなく**重複を除いた日付**で数える。
- **既存データは自動補正しない**: 0〜9時JSTに記録された前日扱いの記録は、`recordedAt`(実際の入力時刻)から推定はできるが、意図的な後入力と区別できないため、勝手に書き換えない。必要なら確認用の一覧を別途出す(Q-A3)。
- **テスト**: `TZ=Asia/Tokyo`・`UTC`・`America/Los_Angeles`の3つで全テストを実行するnpmスクリプトを追加。時刻を固定して、JSTの0:30 / 8:59 / 9:01 / 23:59 で対象日・F10・Danger・レポート・相関を検証。ミューテーション検証(修正前の`addDays`で失敗すること)。ブラウザ(`timezoneId`指定)で0:30 JSTのフォーム既定値を確認。

**コスト: 小〜中(機械的な置き換えが中心) / リスク: 低**

## 事前調査B: 古いService Workerのキャッシュで旧バンドルが動く場合

### 結果
- `public/sw.js`は**ネットワーク優先**(オンラインなら常に最新を取得。オフライン時のみキャッシュ)。したがって「オンラインなのに旧バンドル」は起きにくい。ただし、次の2つで旧バンドルは動く。
  1. **デプロイ前から開いたままのPWA/タブ**: `skipWaiting`+`clients.claim`で新しいSWに切り替わっても、**画面のJSは再読み込みするまで旧版のまま**。スマホのPWAはバックグラウンドに数日残るため、現実的。
  2. **オフライン時**のキャッシュ、および別の端末で作った新しいデータのJSON/Drive復元を旧版の画面で開いた場合。
- **実際の古いコード(コミット`7983a94`)で、現行形式のデータを読み込んだ結果**:
  | フィールド | 旧バンドル |
  |---|---|
  | 日次記録の`entryMode`、**`dangerSymptoms`(危険症状)** | **消える**(`normalizeDailyLog`が既知のキーだけで再構築するため) |
  | ストア直下の未知のコレクション | 消える |
  | 症状の`onsetDate`、検査値の`esrMmH`、服薬の`intake` | 残る(オブジェクトを丸ごと通すため) |
  旧バンドルがその状態で1回でも保存すると、**危険症状の記録が永久に消える**。
- 今後も、日次記録に項目を足すたびに同じ問題が起きる(`SCHEMA_VERSION`は据え置きの追加変更のため、古い版は気付かずに削除する)。

### 設計案(指摘5と一体で実施)
- (a) **未知のフィールドを保持する**: `normalize*`を「既知のキーを正規化しつつ、それ以外は`...entry`で通す」形にする。ストア直下の未知コレクションも保持。→ **今後の**旧バンドルによる削除を防ぐ。
- (b) **書き込み世代の刻印(`storeRevision`)**: ストアに整数の世代を持たせ、現在のコードより新しい世代のデータを読んだ場合は**保存を停止**(読み取り専用)し、「アプリが古いため保存を止めました。再読み込みしてください」と通知する。→ 旧バンドルの破壊的な保存を防ぐ。(c)の補助にもなる。
- (c) **新しい版の検知**: ビルドIDを持つ`/version.json`を、画面がアクティブになった時に取得(no-store)して差異があれば「新しいバージョンがあります。再読み込みしてください」と通知(Q-B2)。
- **限界(正直に)**: (a)(b)は**この版以降**にだけ効く。すでに配布済みの旧バンドル(今開いているタブ)は守れない。デプロイ後は、PWAを一度完全に閉じて開き直すよう案内する必要がある。iOSのPWAの実際の更新挙動は実機で確認できていない。
- **テスト**: 旧バンドルの`migrate`を固定コピーして、現行データを通す回帰テスト(消えないこと)。未知フィールドの往復。世代が新しいデータでの保存停止。

**コスト: 中 / リスク: 中(normalizeの全面変更のため、既存の移行テストで守る)**

## 指摘1: 発熱だけが続いても警告が出ない

### 再現: あり
実コードで確認: 39.5℃が7日連続でも、倦怠感チェックが無ければ**発火しない**(ルートAは発熱+倦怠感、ルートDは倦怠感のみ)。40.0℃が1日でも発火しない。プレドニン服用中(敏感モード)でも同様。

### 設計案(新ルートE「発熱単独」)
| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **E-a** | 7日窓内の発熱日数が、既存の閾値(通常3日/敏感2日)以上 | 既存定数と整合。単純 | 高熱が1日だけでは出ない |
| **E-b(推奨)** | E-a **または** 直近2日以内に高熱の日が1日でもある(**通常39.0℃ / 敏感38.5℃**、暫定) | 短期の高熱を拾える | 風邪等の一過性でも発火しうる |
| E-c | 直近2日連続で発熱(通常38.0/敏感37.5) | 早期に拾える | 単発の高熱は拾えない |

- 高熱の判定を「直近2日以内」に限るのは、一度高熱が出て回復した後の数日、警告が出続けないようにするため。
- **閾値は全て暫定(主治医確認待ち)**。コード内コメントと、警告の理由文に「暫定・主治医確認待ち」と付ける。
- **敏感モードとの整合**: 発熱の判定温度と日数は、既存の`feverThreshold`(通常38.0/敏感37.5)と`feverDaysThreshold`(3/2)をそのまま使う。高熱の温度だけ、敏感時に0.5℃下げる。
- **A/Dとの重複表示**: Aが成立している時は、Aの文言が発熱日数を含むためEの文言は出さない。EとDが同時なら、同じ「発熱・倦怠感」カテゴリに別々の理由として並べる(新カテゴリは作らない)。
- 体温を測っていない日は、発熱の判定に使えない(現状どおり)。

### 影響範囲
`lib/emergencyCheck.ts`(ルート追加、`triggered`の論理和、理由文) / `tests/emergencyCheck.test.ts` / README・仕様書。`EmergencyBanner`は変更不要(カテゴリ表示は汎用)。
### テスト方針
境界値(38.0/37.5/39.0/38.5ちょうど)、日数、直近2日の窓、A成立時に理由が重複しないこと、敏感/通常の差、簡易入力の体温、未測定、ミューテーション検証。

**コスト: 小 / リスク: 低(誤報が増える側の変更のため、閾値の承認が要)**

## 指摘2: 生物学的製剤・免疫抑制薬が「解熱・抗炎症薬の服用中」に入っていない

### 再現: あり
実コードで確認: 「アクテムラ」「トシリズマブ」「ケブザラ」「イラリス」「メトトレキサート」「リウマトレックス」は**全て対象外**。さらに、表記ゆれにも弱い: 「prednisolone」「PSL」「loxoprofen」「ぷれどにん」「ﾌﾟﾚﾄﾞﾆﾝ(半角)」は**対象外**(「プレドニン」「ロキソニン」「プレドニゾロン錠」は対象)。お薬手帳の写真読み取り(LLM)や手入力の表記は一定しない。

### 設計案
- **判定を関数化**: `classifyMedication(name) → カテゴリ[]`。名前を**正規化**(NFKC、小文字化、カタカナ→ひらがなへ統一、空白・中黒・長音の除去)してから、各カテゴリの語(商品名・一般名・英語の一般名)と部分一致。`PSL`/`MTX`/`TCZ`等の**短い略称は、前後が英数字でない場合だけ**一致(誤検知防止)。**外用剤**(軟膏・クリーム・ローション・点眼・点鼻・吸入・貼付・外用)を含む名前は対象外(リンデロン軟膏等での誤って敏感化を防ぐ)。
- **カテゴリ(全て暫定・主治医確認待ち。リストの最終確定は主治医)**:
  | カテゴリ | 例(商品名/一般名) | 敏感モード | CRP注記 |
  |---|---|---|---|
  | ステロイド(既存) | プレドニン/プレドニゾロン、メドロール、デカドロン 等 | ○ | - |
  | NSAIDs・アセトアミノフェン(既存) | ロキソニン、ボルタレン、カロナール 等 | ○ | - |
  | **IL-6阻害薬(新)** | アクテムラ/トシリズマブ、ケブザラ/サリルマブ | ○ | **○** |
  | **IL-1阻害薬(新)** | イラリス/カナキヌマブ、アーカリスト/リロナセプト、キネレット/アナキンラ(国内の承認状況は未確認) | ○ | - |
  | **免疫抑制薬(新)** | メトトレキサート(リウマトレックス、メトレート)、タクロリムス(プログラフ)、シクロスポリン(ネオーラル)、ミコフェノール酸、アザチオプリン | ○(Q2-1) | - |
  | JAK阻害薬・TNF阻害薬(候補) | ゼルヤンツ、オルミエント、リンヴォック、エンブレル、ヒュミラ 等 | 要判断(Q2-1) | - |
- **判定の対象**: 現状は`active`のみ。`isMedicationApplicableOnDate(m, 今日)`(処方開始日・中止日)も併せて見る(開始前・中止後の薬で敏感化しない)。
- **表示の透明化**: 敏感化した理由に、検出した薬とカテゴリを出す(例: 「アクテムラ(IL-6阻害薬)の服用中のため…」)。誤判定を利用者が見抜ける。文言に「暫定・主治医確認待ち」を付ける。
- **CRP注記**: IL-6阻害薬の使用中(その記録日に有効な登録薬)は、検査値の入力欄・記録履歴のCRPタグ・レポートに「IL-6阻害薬の使用中はCRPが低く出ることがあります(暫定・主治医確認待ち)」を出す。**フェリチン/ESR比にも同様の注記を付けることを提案**(IL-6阻害でESRも低下しうるため、比が実際より高く出る可能性。Q2-3)。
- **注意**: 生物学的製剤のCRP・発熱への影響の一般論を注記とするもので、個別の数値の解釈や閾値の変更ではない。

### 影響範囲
`lib/emergencyCheck.ts`(`isOnFeverSuppressingMedication`の置き換え、理由文) / 新規`lib/medicationClassifier.ts` / `DailyLogForm.tsx`・`DailyLogList.tsx`・`ReportView.tsx`(注記) / テスト。既存の`isOnFeverSuppressingMedication`の呼び出し元(`checkEmergency`)は互換を保つ。
### テスト方針
表記ゆれ(半角・ひらがな・英語・略称)、外用剤の除外、短い略称の境界、期間外の薬、カテゴリ別の敏感化、注記の表示条件(IL-6のみ・記録日に有効な薬のみ)、ミューテーション検証。

**コスト: 中 / リスク: 中(薬剤リストの誤りが敏感化・注記に直結するため、暫定であることを画面に明記)**

## 指摘3: 危険なサインの後に記録が途切れると、警告が消える

### 再現: あり(Danger層・F10とも)
| 状況 | 結果 |
|---|---|
| 危険症状を2日前に記録して、それ以降記録なし | **Danger層: 発火しない**(今日と昨日の記録のみが対象) |
| 発熱+倦怠感を3日間記録して、その後記録なし | **F10: 最後の記録が3日前までは発火、6日前だと消える**(7日の観察窓の外に出る)。消えたあとは「該当した記録はありません」という**中立表示に戻る** |
| フェリチン異常 | 14日間は残る(検査値は窓が長い。問題は小さい) |

つまり、**最も危険なサインの後に、体調が悪くて記録が止まった状況ほど、警告が消える**。中立表示の文言は限定的だが、それ自体が「もう問題ない」と読める。

### 設計案(「未解消の注意」)
- **最後に警告条件を満たした日 L を求める**: 直近30日の各日 d について、その日を「今日」としてDanger層・F10を再評価する(**as-of評価**。`checkDanger`・`checkEmergency`に「今日」の引数を追加。その日より後の記録は使わない)。いずれかが発火した最新の日が L。
- **表示条件**: L が存在し、**L より後の日付の記録(スキップ以外)が無い**間、「未解消の注意」を表示する。記録が再開されたら、通常の判定(今日/直近の窓)に戻る。
- **文言(Danger由来)**: 「最後に危険な症状(◯◯)を記録した日(YYYY-MM-DD)以降、N日間記録がありません。**記録がないことは、症状が治まったという意味ではありません。** 体調を確認し、心配な場合は医療機関に相談してください」。F10由来も同様(「注意条件に該当した記録」)。診断ではない旨の免責文を付ける。
- **中立表示との関係**: 未解消の注意を出している間は、「該当した記録はありません」の中立表示は出さない(矛盾するため)。
- **解除条件(Q3-2)**: 記録の再開 / 「確認した」ボタン(その L に対する確認として端末に保存。新しい発火で再表示) / 自動失効は設けない(推奨。ただし、L から長期間(例: 90日)経過したものは弱い表示に切り替える案あり)。
- **F10側の同様の穴**: 上表のとおり、**F10にも同じ穴がある**ため併せて対象にする(Q3-3)。
- 代替案(スナップショット保存: 画面を開いた時の判定結果を保存する)は、開かなかった日の判定が抜けるため不採用。

### 影響範囲
`lib/dangerCheck.ts`・`lib/emergencyCheck.ts`(「今日」引数の追加、as-of評価での未来の記録の除外) / 新規`lib/alertHistory.ts` / `DangerBanner`・`EmergencyBanner`(表示と確認ボタン) / テスト。指摘1・2でF10の中身を触るため、**先にそちらを終えてから実装する**。
### テスト方針
as-of評価が「その日より後の記録を使わない」こと、L の算出(Danger・F10・検査値)、記録再開での解除、スキップは再開に数えないこと、確認ボタンと再発火、中立表示との排他、JSTの日付境界(事前調査Aとの組み合わせ)、ミューテーション検証。

**コスト: 中 / リスク: 中(as-of評価の追加で判定関数の引数が増える)**

## 指摘4: 端末側でデータごと消える経路への備え

### 現状(確認)
`navigator.storage`の使用は**無し**(`persist()`も`estimate()`も未実装)。「最後に外部へバックアップした日時」の記録も**無し**。JSON書き出しは`<a download>`のみ(成功の確認は取れない)。Google Driveバックアップは成功を確認できる。アプリ内のバックアップ(`vitalog:store:backup`)は**同じlocalStorage内**のため、ブラウザがストレージを消すと本体と一緒に消える。

### 設計案

## 指摘5: 保存方式の根本見直し

### 再現: あり
実際の`saveDailyLogs`等で確認: タブAとタブBが同じ状態で開き、Bが記録を追加して保存したあと、Aが別の記録を追加して保存すると、**Bの記録が消える**(`['L1','A-new']`)。同一タブ内でも、変更するフックのインスタンスが2つあれば同様(`['L1','I2']`)。dirtyフラグは「読み込んだだけのインスタンスが書き戻す」事故しか防げていない。

### 設計案(read-modify-write)
- **`lib/storage.ts`に`updateStore(mutator)`を新設**: (1)保存の瞬間に`loadStore()`で**最新を読み直す**(破損検出・自動復旧もそのまま通る)→ (2)変更操作を**id単位**で適用(`upsertById`/`patchById`/`removeById`)→ (3)既存の`saveStore`(temp→読み戻し検証→本キー反映、バックアップ、失敗通知)で保存→ (4)`vitalog:store-changed`イベントを発火。**保存手順・破損復旧・失敗通知は変更しない**。
- **フックは「ストアの写し」にする**: 起動時、`vitalog:store-changed`(同一タブ)、`storage`イベント(他タブ)で`load`し直す。**配列をまるごと書く処理は無くなる**ので、dirtyフラグも不要になる。
- **変更操作の戻り値**: `addLog`等は成否を返す。保存に失敗した場合は状態を更新せず(存在しない記録を表示しない)、`DailyLogForm`は成功した時だけ入力をリセットする(**保存失敗で入力内容が失われない**)。
- **`bulkImport`・お薬手帳の差分更新・通院の検査値反映**も`updateStore`に載せ替える。イベントで画面が更新されるため、`window.location.reload()`は不要になる(Q5-4: 全置換系の復元(JSON/Drive/取り消し)は従来どおり再読み込みを残すことを提案)。
- **並行の扱い**: ストアの読み直しと書き込みは同期(同一のJSタスク内)で、他タブと衝突しうる窓は**マイクロ秒**。(案1・推奨)同期のままで残余リスクを文書化 / (案2)Web Locks(`navigator.locks`)で直列化(非同期化が必要で、呼び出し側の変更が大きい)。
- **同じ記録の同じ項目を別タブで同時に編集**した場合は、後の保存が勝つ(項目単位)。**入力中のフォームの下書きはストアに無いので統合されない**。

### 複数タブの既知の問題は解消するか
**記録単位の上書き消失は解消する**(上記の再現が、`['L1','B-new','A-new']`になる)。残る制約は3つ: (1)マイクロ秒の競合窓(案1) (2)同一項目の同時編集は後勝ち (3)**この版へ更新していない古いバンドルのタブは、依然として配列ごと書く**(事前調査Bと同じ限界。デプロイ後は全タブを再読み込みする必要がある)。`StoreSyncBanner`の「別タブで更新」は、データ保護のためには不要になる(Q5-3: 廃止または控えめな表示への縮小)。

### 影響範囲(洗い出し)
| 種別 | 箇所 |

| 保存の中核 | `lib/storage.ts`(`updateStore`、ヘルパー、イベント) |
