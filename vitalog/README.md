# Vitalog

成人発症スティル病（AOSD）当事者本人のための、体調・服薬・生活負荷を記録するセルフトラッキングPWA。

詳しい背景・設計思想・全機能要件（F1〜F12）は [`docs/requirements.md`](./docs/requirements.md) を参照。

## このセッションで実装した範囲

- **F1: 毎日の体調記録** をフル実装（体温・体調スコア・関節痛・症状(咽頭痛/頭痛/腹痛/筋肉痛+自由追加)・気分スコア・落ち込み理由タグ・服薬記録・自由メモ・音声入力・リンパ節腫れ/皮疹などの任意項目・後入力/スキップ）
- **F2: 服薬記録**（`/medications`）: 定期薬/頓服マスタの登録、減薬・増薬(テーパリング)履歴、Notification APIによるリマインダー（※アプリを開いているタブでのみ動作するフォアグラウンド通知。真のバックグラウンドPushにはService Worker+サーバー側のPush購読管理が必要なため今回のスコープ外）
- **F4: データ可視化**（`/trends`）: 体調/気分スコア・体温・睡眠時間のトレンドグラフ(依存ライブラリなしの自前SVG実装、ホバーで値を表示、7/30/90日/全期間フィルタ)。dataviz運用ガイドの検証済みカテゴリカルパレット(青/オレンジ)を使用
- **F9: スケジュール・負荷管理**: 負荷感(3段階)・活動タグ(カスタムタグ追加可)・睡眠時間を毎日の記録に統合
- **F10: 緊急時検出・受診推奨**: 高熱の持続＋普段と違う強い倦怠感、または検査値(フェリチン/血小板)の急変をルールベースで検知し、記録画面上部に警告バナーを表示。**診断ではなく受診推奨の一次スクリーニングであり、閾値は暫定値**であることを明記（`lib/emergencyCheck.ts`）。F12-4のライフステージ移行期間中は自動的に閾値を敏感化する
- **F3: 環境データ取得**: Open-Meteo(APIキー不要)から気温・気圧・湿度を自動取得。ブラウザのGeolocation APIで位置情報を1回だけ取得しlocalStorageに保存、以降は対象日に応じて現在値/過去データAPIを自動で使い分ける
- **F7: 医師向けレポート出力**（`/report`）: 期間別(7/30/90日/全期間)の統計サマリー(平均スコア・関節痛部位別頻度・服薬一覧・メモ等)を表示し、ブラウザの印刷機能でPDF保存できる
- **F8**: `types/vitalog.ts` の `SCHEMA_VERSION` と `lib/migrate.ts` によるデータバージョン管理・マイグレーション、JSON/CSVエクスポート、JSONからの復元、**Google Driveへのバックアップ**（`NEXT_PUBLIC_GOOGLE_CLIENT_ID`設定時のみ有効。appDataFolderスコープでこのアプリ専用の隠しフォルダにのみアクセス）（`/backup`）
- **F12-1: 仮説検証フレームワーク**（`/experiments`）: 仮説の登録・一覧。統計的な支持率算出はF5/F11(相関分析)実装後
- **F12-2: セルフA/Bテストログ**（`/experiments`）: 介入期間の宣言と、介入前の同じ日数分との体調スコア平均比較（厳密な統計検定ではなく簡易的な目安）
- **F12-4: ライフステージ移行監視モード**: 2027年4月前後90日間を要注意期間として自動フラグし、バナー表示とF10の閾値敏感化を行う（`lib/lifeStage.ts`、日付は要件変更時に直接書き換え）
- **F12-5: 健康×生産性相関記録**: 任意入力の成果実感スコア(1〜10)を毎日の記録に追加
- 自由メモの自動タグ付け（`POST /api/tag-memo`、Claude Haiku利用、`ANTHROPIC_API_KEY`未設定でも記録自体は問題なく動作）
- **写真ベースの自動記録(F1拡張)**: 服薬パッケージ/外用薬パッケージ/血液検査結果票の写真をVision対応LLM(既定はHaiku、`ANTHROPIC_VISION_MODEL`で変更可)に渡し構造化データを抽出。**抽出結果は必ず確認・編集画面(`components/PhotoCaptureButton.tsx`)を経てからDailyLogにマージ**され、無確認で自動保存されることはない。写真本体は既定では破棄し、ユーザーが明示的に選んだ場合のみIndexedDB(この端末のブラウザ内のみ)に保存する。抽出結果はDailyLogの頓服(`medications`, type: asNeeded)・新設の外用薬(`topicalMedications`)・検査値(`labs`、WBC/フェリチン/CRP/AST/ALT/血小板)にそれぞれ反映
- **F2拡張: 服薬管理の抜本改善**（`/medications`）:
  - 過去の処方箋・検査結果票を複数枚まとめてインポートし、書類の日付を対象日として既存の毎日の記録に(上書きせず)追記する一括インポート機能
  - 服薬管理に登録済みの定期薬は、毎日の記録画面でチェックボックス方式(既定: 服用済み)になり、手入力が不要に。頓服は従来通り手動追加
  - お薬手帳の写真から複数の薬・処方日をまとめて読み取り、現在の登録済み薬との差分(新規/用量変更/中止候補)を提示してから、確認したものだけ反映する差分更新機能
  - `lib/settings.ts`によりライフステージ移行日(F12-4)を`/settings`画面から変更可能に
- **通院管理(新規、`/visits`)**: 受診日・病院名/診療科・検査結果の写真(複数可、`PhotoCaptureButton`を再利用)・
  お薬手帳の写真(`MedicationNotebookUpdater`をそのまま再利用)・自由メモ・次回受診予定日をまとめて記録。
  検査値は受診日を対象日として毎日の記録にも自動反映される(`lib/bulkImport.ts`の`applyBulkLabResult`を再利用)。
  次回受診予定は服薬リマインダーと同じ制約(アプリを開いている間のみ)で前日/当日に通知。
  レポート画面(`/report`)にも「直近の通院履歴」として連携表示

F5/F6/F11(相関分析・アラート予測)、F12-3(年次振り返り)は未実装。要件定義書の設計思想通り、データ量に応じて段階解禁する前提の機能(30/90/365日〜)のため、実データが貯まってから着手する。`app/roadmap` に実装状況の一覧がある。

## 設計上の決定

- **サーバーレス・localStorage永続化**: 単一ユーザー・認証不要というスコープに対し、他アプリ（`aws-saa-study`等）と同様にクライアントサイドのみで完結させた。医療データそのものをリポジトリやサーバーに一切置かない方針とも合致する。
- **記録対象日(`targetDate`)と実入力時刻(`recordedAt`)を分離**: 「いつでも記録可能・後入力・スキップ可」という継続性最優先のUX方針を型レベルで表現している。
- **メモのLLMタグ付けは失敗しても記録を止めない**: API未設定・通信エラー時もsilentに失敗し、体調記録自体の入力体験を損なわない。
- **F9の項目は独立レコードにせず、DailyLogのフィールドとして統合**: 「1日の記録は1つ」というF1の設計をそのまま踏襲した方が、相関分析(F5/F11)の際にレコード結合の手間がなく扱いやすいと判断した。
- **F10の閾値はハードコードされた暫定値**: 山口基準等の一般的な目安（38℃の高熱、フェリチン500ng/mL等）を仮置きしている。F5/F11で個人のベースラインが学習できるようになれば、パーソナライズ閾値に置き換える前提。
- **緊急検出はローカルで即時判定**: サーバーへのデータ送信なしにブラウザ内で完結させ、オフラインでも動作する。
- **写真データはDailyLogの外に置く**: `lib/photoStore.ts` (IndexedDB)で写真を管理し、DailyLogには`sourcePhotoId`という参照IDだけを持たせる。これにより写真本体がJSON/CSVエクスポートやlocalStorageの記録データ本体に混入することが構造的にありえない。皮疹写真も当初はlocalStorageにdataURLとして直接埋め込んでいたが、容量制限(5〜10MB程度)によるQuotaExceededErrorのリスクがあったため、他の写真機能と同じIndexedDB方式に統一した。
- **写真からの抽出は確認必須、無確認保存は不可**: 特に検査値はF10の緊急検知に使われるため、LLMの誤読がそのまま記録される事態を型・UIの両方で構造的に防止している(`PhotoCaptureButton`はconfirm操作なしに状態を`reviewing`から先に進められない)。
- **F12-1/F12-2は「枠組みだけ」先に作る**: 支持率の統計算出や有意差検定はF5/F11(相関分析基盤)が前提になるため、今回はデータ構造とUI(登録・一覧・簡易比較)のみ実装し、統計エンジンは後回しにした。
- **Google Driveはappデータフォルダのみ**: `drive.appdata`スコープを使い、ユーザーの他のDriveファイルには一切アクセスしない設計。サーバーを経由せずブラウザ内でOAuthトークン取得からアップロードまで完結させる。
- **バックアップの上書きには必ず退避が挟まる**: JSONインポート・Google Drive復元とも、実行直前の状態を1世代だけlocalStorageに自動退避してから上書きする(`lib/storage.ts`の`importStoreFromJson`)。誤って古い/壊れたバックアップを復元しても、バックアップ画面の「直前の復元操作を取り消す」で戻せる。Google Drive側も単一ファイル上書きではなく日付付きファイル名で直近5世代を保持する。
- **緊急検出は「実際の今日」から見た直近14日以内の記録だけを見る**: 過去の処方箋・検査結果を後から一括インポートした際、それが記録全体の中で最新の日付だと、発病当初のような何年も前の重い数値を「現在の状態」として誤って警告してしまうバグがあった。`EMERGENCY_LOOKBACK_DAYS`で判定対象を直近14日に限定して修正した。
- **服薬管理は「チェック方式」を採用**: 定期薬は登録さえしておけば毎日の記録画面で薬品名・用量を再入力する必要がなく、チェックボックスのオン/オフだけで完結する。既定はチェック済み(服用した)とし、飲まなかった日だけ外す「例外ベース」の入力にすることで、長期継続のハードルを下げつつ、未服用の記録もあいまいにせず明示的に残す(`MedicationRecord.taken`)。
- **お薬手帳の差分更新は必ず確認を挟む**: 複数の薬・複数の受診日が並ぶお薬手帳を解析すると、抽出精度のブレが大きくなりやすい。新規/用量変更/中止候補を提示するだけに留め、実際の反映(特に中止)はユーザーが個別にチェックを入れるまで一切実行しない。
- **通院記録は既存ロジックの呼び出しで構成**: 検査結果OCRは`PhotoCaptureButton`、お薬手帳更新は`MedicationNotebookUpdater`をそのまま埋め込んでいる。お薬手帳側は独自の「この内容で更新」ボタンで即座に確定する設計のため、通院記録本体の保存(受診日・病院名・メモ等)とは別のタイミングで確定される。1つの保存操作に統合する方が理想的だが、既存コンポーネントの再利用を優先した。
- **直接storageを書き換える系の操作は保存後にページを再読み込みする**: 一括インポート・お薬手帳更新は、Reactの状態管理(useMedications等のフック)を経由せず`lib/storage.ts`を直接操作しているため、画面上の一覧が自動更新されない。素朴だが確実な対処として、確定後に`window.location.reload()`している。
- **定期薬に処方開始日/中止日を持たせ、バックフィル入力時のチェックリスト表示を日付で絞る**: 過去日を選んで後入力する際、「対象日の時点でまだ処方されていなかった薬」や「既に中止していた薬」がチェック済みの状態で表示されてしまうと、実際には服用していない薬が「服用した」という誤ったデータになる。`RegisteredMedication.startDate`/`endDate`と`lib/medicationApplicability.ts`の`isMedicationApplicableOnDate`で、対象日がその期間外の薬はチェックリストから除外する。旧データ(startDate/endDate未設定)は後方互換のため常に表示対象として扱う。
- **手動追加の服薬種別変更は既存データを一切変換しない**: チェックリスト方式の導入で、毎日の記録画面の手動追加リストから「頓服」以外の選択肢を無くしたが、これはあくまで入力フォームの変更。`lib/migrate.ts`はDailyLog.medicationsの各要素を素通しするだけで、既に保存済みの`type: "regular"`のデータを書き換えることはない。ただし一覧表示側は`registeredMedicationId`の有無だけで「チェックリスト由来か手動追加か」を判定していたため、この移行より前に手動登録された旧・定期薬記録は「頓服」と誤解されかねない表示になっていた。`DailyLogList`で`registeredMedicationId`が無くかつ`type === "regular"`の場合は「[旧・定期薬記録]」と明示するようにして、データの意味を表示上も保持している。
- **中止済みの薬の名寄せ(お薬手帳更新)**: 減薬後に同じ薬が再処方されるケースで、中止済み(`active: false`)の薬が新規レコードとして重複登録されないよう、`applyPrescriptionToRegisteredMedications`は同名のactiveな薬→同名のinactiveな薬→無ければ新規、の順で名寄せする。中止済みレコードに一致した場合は新規作成せずそのレコードを再利用し、`active: true`・`endDate`クリア・`startDate`を再処方日に更新する(「再開」としてテーパリング履歴にも記録)。`MedicationNotebookUpdater`の確認画面には「再開」という専用カテゴリを設け、旧用量→新用量を表示してから確定させる。
- **バックフィル絞り込みの境界は当日を含む**: `isMedicationApplicableOnDate`は`対象日 < 開始日`または`対象日 > 中止日`のときだけ除外する厳密不等号なので、処方開始日/中止日の当日はチェックリストに表示される。
- **症状記録を咽頭痛専用構造から汎用化**: 「強さ(1〜5)＋普段と違う感覚の有無＋自由記述」という咽頭痛だけに使っていた構造を、`SymptomEntry`として汎用化し、頭痛・腹痛・筋肉痛・自由追加の症状にも使えるようにした(`DailyLog.symptoms: SymptomEntry[]`)。部位選択を伴う関節痛(独自構造のまま)と、所見寄りのリンパ節腫れ・皮疹(汎用化対象外のまま「その他の項目」に残置)は対象外とした。旧`soreThroat`/`musclePain`フィールドは型に残しつつ`@deprecated`として非推奨化し、新規データはもう書き込まない。`lib/migrate.ts`が読み込み時に旧データからsymptomsを合成するため、過去データも表示・レポート集計に反映され続ける。
- **睡眠は「入眠時刻＋睡眠時間」の組み合わせで記録し、起床時刻そのものは保存しない**: 当初「入眠時刻＋起床時刻」の2つの時刻を独立に保存する案を検討したが、日をまたぐ睡眠(23時就寝→翌7時起床)の場合、起床時刻側にどの日付を紐付けるかが曖昧になる(起床時刻の`targetDate`は前日か当日か等)。睡眠時間(`DailyLog.sleepHours`、既存フィールドを流用)は入力者が直接把握している値なので、入眠時刻(新設の`sleepStartTime?: string`、HH:mm)と組み合わせれば日付を跨ぐケースでも曖昧さが生じない。起床時刻が見たい場面(フォーム上の表示のみ)は`入眠時刻+睡眠時間`から算出して見せる、保存はしない。`sleepStartTime`は追加のオプショナルフィールドなのでスキーマバージョンは上げていない。
- **症状チップは記録頻度順に並べ、頻出の自由入力症状は常設チップに昇格させる**: 咽頭痛・頭痛・腹痛・筋肉痛という既定候補の並び順を固定にせず、過去の`DailyLog.symptoms`から症状ごとの記録日数を集計し、多い順に並べ替える(`DailyLogForm`内の`symptomFrequency`)。自由入力で2回以上記録された症状名は、次回以降は都度自由入力欄から探さなくて済むよう既定候補と同じ常設チップ扱いにする。別途の履歴ストレージは持たず、既存の記録データから毎回集計するだけなのでデータ構造の変更は不要。自由入力欄には過去に使った症状名を`<datalist>`で入力候補として出す。
- **睡眠不足×症状の相関はレポート画面のみに追加し、閾値はハードコード**: 「睡眠時間が6時間未満だった日の翌日」と「それ以外の日の翌日」とで、何らかの症状(症状記録・関節痛・普段と違う倦怠感のいずれか)があった割合を比較する(`lib/report.ts`の`buildSleepCorrelation`)。閾値(6時間)や比較窓(翌日1日のみ)を設定画面で変更可能にする案もあったが、現時点ではデータ量が少なく閾値を可変にしても意味のある比較にならないため、まずは固定値でレポートに出し、様子を見て設定化を検討する方針にした。
- **F10緊急検知は「発熱に依存しない」複数ORルートで再設計(発熱マスキング対応)**: ステロイド・NSAIDs・解熱鎮痛薬の服用中は発熱が薬理学的に抑制され、38℃まで上がらないまま病状が悪化しうる。発熱依存の検知は治療がうまくいっている時ほど見逃すため、`lib/emergencyCheck.ts`を4つの独立ORルートに再編した:(A)持続発熱かつ持続倦怠感、(B)検査値異常(フェリチン高値/血小板低値。検査値は疎なので直近14日窓から各項目の最新値を個別探索する)、(C)症状の急変(関節痛の急増=直前3件平均からのデルタ超過かつ最大強さ3以上、重い新規部位=強さ3以上の新部位、皮疹の新規出現)、(D)発熱を伴わない倦怠感の遷延(通常4日/敏感時3日で単独発火。発熱マスキングの本命ルート)。さらに、登録済みの薬にactiveな解熱・抗炎症薬(名前の部分一致による発見的判定。`isOnFeverSuppressingMedication`)がある場合は`feverSuppressed`として発熱閾値を38.0→37.5℃に下げ、非発熱ルートも敏感化する。「急増」は個人差を考慮し絶対閾値ではなく直近平均からの乖離で定義し、偽陽性抑制のため最低強さ(3以上)を併せて要求する。ストリーク窓は閾値と切り離して固定7日とし、敏感化時に必要日数が窓を超える不整合を解消した。EmergencyBannerは発火理由を「発熱・倦怠感/検査値/症状の急変」のカテゴリ別に表示する。これらの閾値・薬名リストは暫定値であり、F5/F11の個人ベースライン学習で置き換える前提。
- **保存はtemp書き込み→読み戻し検証→本キー反映、破損時はtemp/backupから自動復旧**: `localStorage.setItem`自体はキー単位でアトミックだが、想定外の原因で本キー(`vitalog:store`)が壊れる/消える事態(数年分のデータ消失が最悪の既知リスク)に備え多重化した(`lib/storage.ts`)。保存フロー:(1)保存直前の本キーの値が**parse可能な時だけ**`vitalog:store:backup`へ退避(壊れた値でbackupを潰さず最後の正常データを守る)、(2)`vitalog:store:temp`へ新データ書き込み、(3)tempを**読み戻してparse検証**、(4)検証OKなら本キーへ反映しtemp削除、(5)検証NGなら本キーに一切触れない。読み込み時に本キーのparseが失敗したら`temp`(保存途中クラッシュ時の最新意図データ)→`backup`(最後の正常データ)の順で復旧を試み、成功時はフラグを立てて次回起動時に`RecoveryNoticeBanner`で通知する。複数タブ同時編集の競合(後保存が先の変更を上書き)には`StoreSyncBanner`で対応:`storage`イベントで他タブの本キー更新を検知し通知するが、記入途中のフォームを失う方がリスクが高いため**自動リロードはせず**再読み込みするか本人に委ねる。
- **F5/F6/F11(相関分析)は段階解禁ではなく連続的な信頼度表示に変更、F12-3(年次振り返り)は不要と判断し削除**: 要件定義書では「30/90/365日でデータ量に応じて段階的に機能を解禁する」設計だったが、本人の意向で「少ないデータでも計算だけはして見せてほしい」という方針に変更した。`lib/correlationAnalysis.ts`の`computeLagCorrelations`は、睡眠時間・生活負荷・気圧の前日比・気分スコアの4つのpredictorと、体調スコア・関節痛の強さ・症状の強さ合計の3つのoutcomeについて、0〜3日のラグでPearson相関係数を計算する(pandas/scipyは使わずTypeScriptで最小実装)。サンプル数5未満または|r|<0.3の組み合わせは除外し、残りをサンプル数に応じて「参考程度(n<15)/傾向あり(n<30)/一定の信頼度(n≥30)」の3段階ラベルを添えて`/trends`画面下部(`CorrelationInsights`)に表示する。要件定義書の実装方針に「F5/F11のコアロジックは本人が自分で設計・理解しながら進める(ポートフォリオの説明責任のため)」とあるため、この実装は確定仕様ではなく「叩き台」の位置づけとし、変数の選定・閾値・言い回しは本人のレビュー・手直しを前提にしている。F12-3(年次振り返りレビュー)は「無くてもよいかもしれない」との判断で、`/roadmap`の一覧から削除した(要件定義書自体は変更していないので、復活させる場合は`docs/requirements.md`を参照)。

- **Danger層(危険症状の独立検知)をF10と完全に分離(ChatGPTサードオピニオン対応)**: F10(ルートA〜D)は「AOSDの活動性・再燃」を推定するロジックだが、息苦しさ・胸痛・失神・強い動悸・急激なむくみ・強い腹痛・異常な出血/黒色便・急激な全身状態の悪化は、再燃かどうかに関係なく相談を促すべき症状で、性質が違う。これらを`DailyLog.dangerSymptoms`(チェックボックス複数選択、既定は全て未選択)として記録し、1つでも選ばれたら`lib/dangerCheck.ts`が即座に発火して、赤の太枠・🚨の`DangerBanner`をF10のバナーとは別に表示する。両者は互いに影響しない独立したif。対象は実際の今日と昨日の記録のみ(後入力や過去記録のインポートで古い症状が「今」の警告にならないようにするため。昨日を含めるのは前夜の記録を翌朝拾うため)。文言に「緊急性が高いと感じる場合は救急要請(119)も」を1行加えている。
- **服薬記録を「服用/未服用/未確認」の3状態に(既定は未確認)**: 従来は既定で「服用済み」にして外した日だけ記録する設計だったが、これだと確認していない日・記録し忘れた日が「飲んだ」に見えてしまい、医師向けレポートにも誤った服薬状況が載る。`MedicationRecord.intake`を3値とし、フォームの既定は未確認。入力の手間を増やさないため「いつも通り全部服用した」ボタンで全ての定期薬を1タップで服用にできる。既存データは読み込み時(`lib/migrate.ts`)に、明示的に外されていた(`taken === false`)ものは未服用、それ以外(旧・手動記録を含む、記録がある=服用として扱われていたもの)は服用に移行する。旧データに「未確認」だった日を識別する情報は無いため、既存の「服用」の中に実際は確認していない日が混ざっている可能性は残る。レポートには定期薬ごとの服用/未服用/未確認の日数を追加し、未確認が服用に混ざらないようにした。
- **F10は「記録がない日」を「症状がない日」として扱わない**: 従来は最新記録から遡った「連続」で判定していたため、(1)1日スキップすると連続が途切れる(体調が悪い日ほどスキップしやすい)、(2)最新記録が古くても「今」の警告になる、という問題があった。今日を含む直近7暦日の窓で、記録がある日だけを数える方式に変更した。欠測・スキップ日は分子にも分母にも入れない。窓内の記録が4日未満の場合は「判定精度が下がっています」と表示し、記録が全く無い場合は「判定できていません」と表示する(`dataQuality`)。症状の急変(ルートC)は最新の記録が3日以内の時だけ評価する。発火しなかった時の表示は、安全宣言に読めないよう「現在、設定された注意条件に該当した記録はありません。この判定は体調に問題がないことを意味するものではなく、記録された内容に基づく参考情報です」に変更した。
- **F10の検査値にWBC・AST/ALTを追加(閾値は暫定・要確認)**: 従来のフェリチン/血小板の判定はそのまま維持し、OR条件として追加した。WBCは3,500/μL以下(低下側のみ。血球減少を拾うため)、AST/ALTは100 U/L以上(基準上限約40の約2.5倍)。**これらは一般的な基準値を参考にした暫定値で、主治医に確認して置き換える前提**(コード内に「要確認」と明記)。WBC高値は、ステロイド服用中は普段から高く常時警告が出ると本当の警告が埋もれる(警告疲れ)ため、単独では発火させない。AST・ALTは同じ肝機能の指標なので1系統として数える。フェリチン/血小板/WBC/肝酵素のうち2系統以上が同時に異常な場合は、「複数の検査値に変化があります。主治医へ共有することを検討してください」を先頭に太字で出す。

- **保存処理の3つの穴を修正(復旧の網羅性・破損データの保全・保存失敗の可視化)**: (1)本キーが「JSONとしては読めるが形が壊れている」(`null`/`{}`/`[]`/version違い等)場合、従来はparse失敗時しか復旧を試みず、`migrateToLatest`が黙って空のストアを返して次の保存で全データが消えていた。`isStoreShape`(version一致かつ`dailyLogs`が配列)で形まで検証し、不正なら破損として扱う。backupの更新・復旧候補の選別・JSON復元(`importStoreFromJson`)も同じ検証を通すため、形が不正なファイルの復元で空データ上書きされることも無い。(2)復旧の可否にかかわらず、破損した本キーの生テキストを`vitalog:store:corrupt-snapshot`へ退避し(次の保存で本キーが上書きされても元の文字列が残る)、復旧できなかった場合は「保存されていたデータを読み込めず、復元できるバックアップもありませんでした」と通知する。バックアップ画面から退避データを書き出せる。同じ破損に対して通知は繰り返さない。(3)`saveStore`は成否を返し、失敗時は`SAVE_FAILED_EVENT`を発火して`SaveFailureBanner`が「データを保存できませんでした」と通知する(従来は握りつぶされ、画面上は保存済みに見えたまま記録が失われた)。バックアップの更新だけが失敗した場合は補助扱いで保存を続行する。復旧通知は、各ページのデータ読み込みより先にバナーが初期化されるため`verifyStoreOnStartup`で起動時に自分で整合性チェックを行う(従来は通知が次回起動まで遅れ、データを読み込まないページでは検出自体されなかった)。ブラウザ(本番ビルド)で復旧・復旧不能・保存失敗の各バナーを実際に確認済み。

- **低エネルギーモード(簡易入力、P1機能3)**: 体調が悪い日でも、ほぼタップだけで最低限の記録を残せるようにした。ホーム最上部の「😣 今日はしんどい(簡易入力)」ボタン、およびPWAのホーム画面ショートカット(`manifest.json`の`shortcuts`、`/?mode=quick`)から開く。項目は体調スコア(1〜10の大ボタン)・「普段と違う強い倦怠感」・症状なし/あり(ありなら頻度順チップ)・**危険症状(常に表示)**・体温(任意)。倦怠感・体温・危険症状を含めたのは、F10(ルートA/D)とDanger層への入力が、最も具合の悪い日に欠落しないようにするため。通常入力と同じスキーマで保存し(`DailyLog.entryMode: "quick"`)、記録履歴の「簡易記録」タグ付きの行から「詳細を追記」できる(通常フォームを開き、簡易入力でカバーした項目をプリフィル。保存時は`mergeAppendedLog`で統合し、カバー外の項目は追記側が空でも既存の値を消さない)。定期薬は該当薬を「未確認」で自動追加する(記録していない=服用した、ではない)。**簡易記録は関節痛・皮疹・睡眠・服薬詳細を聞いていないので「なし」の根拠にしない**: F10のルートC(症状の急変)は簡易記録を比較の基準にも最新の記録にも使わず(空の関節痛との比較で新規部位を誤検知するため)、相関分析は関節痛の強さ・症状の強さ合計の結果変数から簡易記録を除外し(未入力を0として扱わない)、睡眠と翌日の体調の比較は「症状も倦怠感も無い簡易記録の日」を材料にしない。一方、倦怠感・危険症状・体温は聞いているのでF10のルートA/D・Danger層・データ充足判定(記録日)には数える。症状「あり」だけで症状名を選ばなかった場合は「症状あり(詳細未入力)」として記録し、頻度順チップ・入力候補には混ぜない。症状「なし/あり」を未回答のまま保存した場合は症状なしとして保存される(回答有無の区別は保存しない)。
- **フック(`useDailyLogs`等)は、変更したインスタンスだけが保存する(データ消失の不具合修正)**: 従来は、データを読み込んだだけのインスタンスも読み込み直後に保存し直していた。簡易保存の直後に通常フォームが作り直されると、その中の`useDailyLogs`が「保存前の古い一覧」を読み込んで書き戻し、追加した記録が消える不具合が、機能3のブラウザ確認で見つかった(従来は通常フォームが常に表示されたままで表面化していなかった潜在的な危険)。5つのフックすべてを、add/update/delete等の変更操作を行ったインスタンスだけが保存する方式(`dirty`フラグ)に変更した。単体テストで、修正前の挙動ではこの消失が再現して失敗することを確認済み。

- **フェリチン/ESR比は「参考値」として表示するだけで、F10の判定には使わない(P1機能2)**: 検査値にESR(`labs.esrMmH`、mm/h)を追加し(手入力・写真読み取り・一括インポート・通院記録)、同じ日のフェリチンとESRが揃っている場合だけ`lib/ferritinEsrRatio.ts`が比を計算する(別の日の値は組み合わせない、ESRが0以下なら計算しない)。閾値21.5の**一次資料は未確認**で、確認できた範囲では、これは成人AOSDではなく**小児の全身型若年性特発性関節炎(sJIA)のMAS**で報告された基準とする二次的な記述に留まり、同じ指標でも研究によりカットオフが異なる(sJIAで「>80」とする報告もある)。成人AOSDでの妥当性は未検証。そのため、入力フォーム・記録履歴・レポートに「参考値」として表示し、超過時は「小児の研究で報告された基準で成人での有効性は確認できていない」旨を含む注意書きを出すが、赤いF10バナーは出さず、複数異常の数にも数えない(未検証の閾値で「受診を検討」と言い切ると誤報による警告疲れや過大な不安につながるため)。一次資料で成人AOSDへの適用が確認できたらF10への組み込みを再検討する(コード内コメントに確認状況を明記)。当初想定した「既存のCRPアラート」は実在せず(CRPは入力・表示のみ)、CRPは比の計算に使わない。
- **検査値の一括インポートで、読み取れなかった項目が既存の検査値を消す不具合を修正**: `applyBulkLabResult`は「上書きせず追記」のはずが、`{ ...既存, ...新規 }`のため、読み取れなかった項目(`undefined`)がその日の既存の値を消していた。ESR追加で影響が広がるため、`undefined`の項目は既存の値を残すよう修正した。

- **前駆症状の順列は「発症日」だけを保存し、順序は日付から導く(P1機能1、データ構造まで)**: `SymptomEntry.onsetDate?`(その症状が始まった日)を追加し、症状ごとに「いつから」([この日から][1日前から][2日前から][日付を指定])を選べる。既定は「この日から」(保存する値は無し)なので追加のタップは要らず、遡りたい時だけ1タップ。発熱・倦怠感・関節痛・皮疹は既存の日次記録から導けるため新規入力は無い。順序そのものは保存せず、`lib/symptomSequence.ts`が毎回、(1)項目ごとの出現のかたまり(出現日の間隔が3日以内)から発症イベント(`declared`=申告/`derived`=記録上の初出日)を作り、(2)発症日の間隔が7日以内のものを再燃エピソードにまとめ、(3)発症日ごとの段(同日は同じ段)に並べて「咽頭痛 → 倦怠感 → 関節痛 → 発熱」のような順列にする。分析ルール(区切りの日数など)を変えても保存データの移行が要らない。採用しなかった案: 配列順(チップをタップした順に意味は無い)、連番(日をまたぐと矛盾し修正が困難)、入力時刻での自動順序付け(発症時刻ではなく入力時刻でしかなく、後入力で崩れる)。粒度は日単位(時刻入力は体調が悪い日の負担が大きい)。**F10(再燃検知)には組み込まない**: 本人は風邪をひきやすく、「喉の痛み→倦怠感→関節痛」は風邪でも起きるため、パターンが未知のまま順列で発火させると誤報による警告疲れで本当の警告が埋もれる。過去の実際の再燃エピソードを見てパターンが確認できてから再検討する(変更箇所は`emergencyCheck.ts`に新ルートを足す形で、影響範囲は設計ドキュメント参照)。パターン分析のUIは未作成。

- **相談チャット「Vitalog Assistant」(`/chat`、`/api/chat`)**: 記録の要約をもとにパターンを整理するチャット。**診断・治療・緊急性の判定はしない**。構成は(1)サーバーで直近2回のユーザー発言を`detectSafetyTrigger`で検査し、危険症状・自傷の表現があればLLMを呼ばず固定文(医療機関/119、いのちの電話等)を返す、(2)それ以外は`buildSystemPrompt`(制約・データ規則・`<app_state>`(F10/Danger層の現在状態)・`<known_limitations>`・`<data_summary>`)でLLM、(3)返信を`sanitizeReply`で検査(安心の断定・診断の断定・治療の指示・緊急性の判定は定型文に置換)。要約(`buildChatSummary`)は端末内で直近30日分を集計して送る(生データ・写真は送らない、自由メモはオプトイン、初回に同意画面、送信内容は画面で確認可)。会話は保存しない。**意図的な逸脱**: 制約9は「医師に相談」を「早めに主治医または医療機関に相談」とした(緊急時に主治医だけを案内しないため)。**日付ずれ(JST 0〜9時、既知の不具合)が直るまで、翌日の体調や睡眠など「日をずらした」分析は要約に含めず、AIにも提供しない**と明示する。**実際のLLMの応答は未検証**(APIキー無しの環境で作成。固定文・フィルタ・要約・プロンプト構築・APIルートは単体テストとブラウザで確認済み)。`ANTHROPIC_API_KEY`(任意で`ANTHROPIC_CHAT_MODEL`)を設定後、`docs/chat-eval-cases.md`の質問で実機評価すること。

`.env.local.example` を `.env.local` にコピーして使う。

- 自由メモの自動タグ付け・写真からの自動記録には `ANTHROPIC_API_KEY` が必要（未設定でも他機能は動作し、自動入力機能だけ手動入力にフォールバックする）
- Google Driveへのバックアップには `NEXT_PUBLIC_GOOGLE_CLIENT_ID` が必要。Google Cloud ConsoleでDrive APIを有効化し、OAuthクライアントID(ウェブアプリケーション)を発行して、承認済みのJavaScript生成元にデプロイ先URLと`http://localhost:3000`を登録する（未設定でも他機能は動作し、Driveバックアップだけ「未設定」表示になる）

## テスト

安全性に直結する部分(F10緊急検知 `lib/emergencyCheck.ts`、保存・自動復旧 `lib/storage.ts`、複数タブ検知 `components/StoreSyncBanner.tsx`)は、Vitest(jsdom)でユニットテストを整備している。

```bash
npm test
```

- `tests/emergencyCheck.test.ts`: ルートA〜Dの発火/非発火(境界値ちょうど含む)、解熱薬服用中・ライフステージ移行期間中の敏感化、検査値の14日窓、ストリークの連続性と7日固定窓、複数ルート同時成立時の理由表示
- `tests/storage.test.ts`: 保存↔読み込みの往復、temp検証失敗時に本キーが不変であること、temp→backupの順の自動復旧、壊れた本キーでbackupを上書きしないこと

- `@/`エイリアスは `vitest.config.ts` で解決している。アプリ本体のコードはテストのために変更していない

- 実装を意図的に壊して(閾値の変更・分岐の削除など多数のパターン)テストが失敗することを確認済み(ミューテーション検証)
